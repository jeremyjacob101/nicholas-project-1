# Secure Research Image Uploads

Local full-stack demo for private research-image storage with React, Express, PostgreSQL, and MinIO.

## Quick start

Prerequisites: Node.js/npm and Docker Desktop.

```sh
cp .env.example .env
npm ci
docker compose up -d --wait postgres minio
docker compose ps
docker compose exec -T postgres psql \
  -U research_uploads_user \
  -d research_uploads < server/sql/schema.sql
```

If you need to discard an older local database and MinIO bucket, run this before the `docker compose up` command above:

```sh
docker compose down -v
```

Change `research_uploads_user` and `research_uploads` to values from your .env if you want your own credentials.

The schema command creates the tables and seeds Alice at Hospital A and Bob at Hospital B. The API creates the private `research-images` bucket automatically when it starts.

Start the API and frontend in separate terminals:

```sh
npm run server
npm run dev
```

Open <http://localhost:2513>. The API health check is <http://localhost:2514/health>.

### Local services

| Service       | Address                 | Local login                                                                      |
| ------------- | ----------------------- | -------------------------------------------------------------------------------- |
| Frontend      | <http://localhost:2513> | —                                                                                |
| API           | <http://localhost:2514> | —                                                                                |
| PostgreSQL    | `localhost:5432`        | `research_uploads_user` / `local-postgres-password`, database `research_uploads` |
| MinIO API     | <http://localhost:9000> | server-only                                                                      |
| MinIO console | <http://localhost:9001> | `local-minio-admin` / `local-minio-password`                                     |

The values above are local dummy credentials from `.env.example`. Change them in `.env` for a different local setup; never commit `.env` or real credentials.

Stop or restart Docker services:

```sh
docker compose stop
docker compose start
docker compose down
```

`docker compose down -v` also deletes the local PostgreSQL and MinIO volumes. Use it only when you intentionally want a clean local database and bucket.

## What the application does

The frontend exposes a development user switcher for Alice and Bob. They belong
to different hospitals, and the selected user is sent as the `X-Dev-User-Id`
header on upload and download requests. The backend resolves that ID and scopes
every upload query to the verified user’s company. This is intentionally a
development identity switch, not production authentication.

The page contains an image upload form and a company-scoped upload list. Active
records are polled every 250 ms until they reach a terminal status, and completed
records can be downloaded through a short-lived presigned URL.

### Data model

- `companies` stores Hospital A and Hospital B.
- `users` associates each development user with a company.
- `uploads` stores sample ID, filename, classification, owning company, creator, generated object key, status, and timestamps.

PostgreSQL stores metadata and authorization data. MinIO stores the actual image bytes. Keeping them separate lets the database handle queries and access control while object storage handles binary files; the database never stores image bytes.

### Upload flow

1. The browser sends metadata, MIME type, and byte length to `POST /api/uploads/init`.
2. The backend validates the request, resolves the current user, generates the upload ID and company-scoped object key, and creates a `queued` record.
3. The backend returns a five-minute presigned MinIO PUT URL.
4. The browser uploads the bytes directly to MinIO with that URL.
5. The browser calls `POST /api/uploads/:uploadId/confirm`.
6. The backend verifies the object exists, validates its stored size/type, marks it `uploaded`, and returns immediately. A simulated background job then advances it through `queued → processing → completed`. The demo includes a three-second in-process processing step. Missing objects, invalid files, processing errors, and timeouts become `failed`.
7. The UI polls the authorized upload list while records are active and displays errors/statuses.

Object keys are generated by the backend in the form `uploads/{company-id}/{upload-id}/{safe-filename}`. The client cannot choose an arbitrary key.

### Download flow

The browser requests `GET /api/uploads/:uploadId/download`. The backend first verifies the current user and company-scoped upload record, checks that the object exists, and only then returns a five-minute presigned MinIO GET URL. The bucket remains private; no public or permanent object URL is used.

Presigned URLs are safer than exposing MinIO credentials because they grant temporary access to one operation and object. They do not replace application authorization: Hospital B cannot obtain Hospital A’s URL because authorization happens before the URL is generated. Cross-company and missing records use the same non-revealing response.

## Tests and verification

Run the complete suite:

```sh
npm run test
```

Unit tests cover validation, storage errors, authentication middleware, processing failures/timeouts, and frontend polling. Integration tests use isolated PostgreSQL and MinIO containers, so they do not use the normal local database or bucket.

Additional checks:

```sh
npm run test:unit
npm run test:integration
npm run test:e2e
npm run typecheck
npm run lint --workspace=client
npm run build --workspace=client
```

`npm run test` runs unit, integration, and browser E2E tests. The E2E suite starts a dedicated Docker Compose project with disposable PostgreSQL and MinIO volumes, seeds the schema, launches the API/frontend against those services, covers Alice’s browser upload/download flow, Bob’s cross-company denial, and visible validation errors, then removes the dedicated project and its volumes. It does not touch the normal local development database or bucket.

The required authorization tests cover Hospital A creating/accessing its own record, Hospital B being denied Hospital A’s record and download URL, and invalid or missing upload metadata being rejected.

## Production considerations

The demo simulates processing in-process. Production processing should enqueue a durable job after confirmation; a worker would claim the job, update `processing`, perform inspection/transformation, and update `completed` or `failed` with retries and idempotency.

Next production improvements would include real authentication/session handling, rate limits, durable job processing, object lifecycle policies, structured logs/metrics, and stricter operational secret management.
